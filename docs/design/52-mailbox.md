# 52. 系統信箱與更新公告

發放項目與版本公告的收納處。**全部由本機觸發，沒有遠端發放**
—— 目前是離線 client-only，`leaderboard-worker` 只有唯讀端點。

| 項目 | 規則 |
|---|---|
| 入口 | `PanelDock` 一顆按鈕 |
| 範圍 | **角色獨立**，每隻角色各自的信箱 |
| 期限 | 未領取**不過期**；已領取的在換版時清掉（§ 52.7.1） |

## 52.2 發放來源

全部是本機判定，觸發條件寫在 seed：

| 來源 | 觸發時機 |
|---|---|
| **天賦格** | **每 5 級 +1 個 T1 天賦格**（`51-auto-talent.md` § 51.3.3.2） |
| 里程碑 | 角色達成指定條件（等級、統計數值） |
| 補償 | **偶發**，由 seed 逐筆列出。**不是每次版本更新都發**。版本範圍見 § 52.2.4 |

**每一筆發放都帶 `sourceKey`**，用來說明這封信是什麼（顯示與除錯）。
**它不是重複發放的防線** —— 見 § 52.2.3。

### 52.2.1 版本更新不發信（硬性）

**更新公告不產生信件。** 版本更新走 § 52.6 的公告分頁，那是一份**累積的清單**，
不是一封一封的信 —— 每版一封信會讓久沒玩的玩家一開信箱看到一長串沒有內容的通知，
而那些通知本來就沒有要給他任何東西。

**補償是偶發事件**：只有真的要補東西時才在 seed 加一筆，多數版本不會有。
它涵蓋哪些版本由條目自己宣告（§ 52.2.4）。

### 52.2.2 補償綁哪個版本（硬性）

**補償一律綁 `BUILD_INFO.version`（顯示版本），不可綁 `CURRENT_DATA_VERSION`。**

`CURRENT_DATA_VERSION` 一升，`19-account-character.md` § 19.9 會**刪光所有舊角色**
（先封存遺產）。升級後留下的都是新角色，從沒經歷過舊版本，補償沒有對象。

**新角色不領舊補償**：每筆補償帶 `publishedAt`，只發給
`character.createdAt < publishedAt` 的角色。沒有這條，新玩家一開檔就會收到
一堆他從沒遇過的問題的補償。

### 52.2.3 發放進度記在角色上（硬性）

**防重複發放的依據是角色身上的「發過幾封」，不是信箱裡有沒有那封信。**

信是可以刪的：換版清理會刪已領取的（§ 52.7.1），玩家也能手動刪（§ 52.4）。
拿信當證據的話，刪完那一輪，下次載入角色就會整批重發 ——
玩家每次改版都多領一批天賦格，而且看起來完全正常。

| 來源 | 記什麼 | 存在哪 |
|---|---|---|
| 天賦格 | 已發過幾封 | `characters.talentSlotGrants` |

發信與記數**必須同一個交易**：只發信沒記數會重發，只記數沒發信會讓玩家永久少一個格子。

計數只增不減，所以每次載入角色、每次升級都可以叫，重複呼叫安全。

#### 52.2.3.1 既有重複資料要對帳

**改對判斷方式不會讓已經發出去的重複資料消失。** 修正時要一次性對帳：

| 對象 | 處理 |
|---|---|
| 同一個 `sourceKey` 的多封信 | 只留一封。**有領過的留領過的那封** |
| 兩封以上都領過 | 每多一封就是多拿一份，收回等量的天賦格 |
| 收哪些天賦格 | **只收沒安裝、沒鑲東西的 T1 格**。裝在配置上的、鑲了鑲材的、合成過的高階格一律不動 —— 動了會讓玩家的配置崩掉 |
| 發放計數 | 重算成等級推導的應發封數，之後照上表只增不減 |

對帳寫在**新的一個 DB 版本**，不可併進已經發布過的版本 ——
那些裝置的 upgrade 已經跑完，改內容也不會再執行。

### 52.2.4 補償的版本範圍

**一筆補償由條目自己宣告它涵蓋哪些版本**，程式不做「這隻角色算不算舊」的判斷。

| 範圍 | 意思 | 適用 |
|---|---|---|
| `this-version`（預設） | 只在 `version` 那一版發。版本一更新就自動失效 | 多數補償。代價是整版都沒上線的玩家收不到 |
| `until` | 發到 `untilVersion`（不含）之前為止 | 隔幾版再上線也還要補，但不想永遠掛著 |
| `all-versions` | 不管跑到第幾版都補 | 漏掉就回不來的東西 |

版本比大小是**數字比不是字串比** —— `1.10.0` 要大於 `1.9.0`。

#### 52.2.4.1 起始配置改版不補發（硬性）

**起始配置（`51-auto-talent.md` § 51.7）加東西時，不補給既有角色。**

它與一般補償的差別是「舊角色」的定義會隨時間一直存在，不像 bug 補償有明確的發生區間 ——
留著就是一條永遠活著、永遠可能判錯的分支。既有角色少拿的部分靠正常掉落與合成補回來。

#### 52.2.4.2 寄送紀錄（硬性）

寄送紀錄記在 `characters.sentMailKeys`：**補償 key → true/false**。不另開表。

| 規則 |
|---|
| 判斷「寄過沒有」看 `sentMailKeys`，不看信箱 |
| 發放 ＝ 補償清單與已寄 key 的差集 |
| 版本範圍不符而沒寄的**不記** |
| 發信與記 key 必須同一個交易 |
| `id` 是身分，用過的 `id` 不可再給另一筆補償 |

#### 52.2.4.3 範圍由使用者決定（硬性）

**新增補償條目前一定要先問使用者要哪一種範圍，不可自己挑預設值。**

範圍選錯的後果不對稱且都很糟：選太窄，該補的玩家永遠收不到；
選太寬，那筆補償一直掛著被檢查，或讓玩家重複收到。
這是「誰該被補到」的產品決策，只有知道那次事故影響範圍的人答得出來。

## 52.3 發放項目的型別

| 型別 | 內容 | 領取後去哪 |
|---|---|---|
| 道具 | `itemId` ＋ 數量 | 背包「一般」分頁 |
| 金幣 | 數量 | 角色金幣 |
| 天賦格 | tier（T1~T4） | 背包「天賦」分頁，**未安裝狀態** |
| 鑲材 | `definitionId`（＋ `boundParam`） | 背包「天賦」分頁 |

一封信可以帶多個項目。

## 52.4 領取規則

| 項目 | 規則 |
|---|---|
| 觸發 | **手動領取，不自動入包** |
| 單位 | 可單封領取，也可「全部領取」 |
| 容量檢查 | **道具要查**（`35-inventory-constraints.md` § 35.3.1）；天賦格不佔格，一律放行 |
| 部分領取 | **不做** —— 背包放不下就整封擋下，不可只領其中幾樣 |
| 已領取 | 保留到下次版本更新為止（§ 52.7.1）。可**單封刪除**，也可「清除已領取」一次清光 |
| 刪除範圍 | **只有已領取的刪得掉**。未領取的沒有刪除鈕 |

**背包放不下時整封擋下**：允許部分領取會讓「這封還剩什麼」變成要另外存的狀態，
而信件本身沒有可變欄位。玩家清出空間再領即可。

## 52.5 未讀提示

`PanelDock` 的信箱按鈕顯示**未領取封數**的數量徽章
（配色與字級見 `34-ui-guidelines.md` § 34.10）。

與自動天賦的「有沒有」小點不同：**信箱的數量是玩家要行動的次數**，
「有 3 封沒領」與「有 1 封沒領」是不同的事；自動天賦的條數則回答不了任何問題。

**指示器只掛在「領取」上，不可掛在「安裝」上。** 領取是待辦（領完歸零），
安裝是玩家的配置決定（囤著合成是正常玩法，見 `51-auto-talent.md` § 51.3.4.1）。
兩者共用同一個指示器會讓它永遠亮著。

## 52.6 更新公告

| 項目 | 規則 |
|---|---|
| 資料來源 | seed，隨版本更新 |
| 內容 | 版本號 ＋ 條列變更 |
| 形態 | **一份累積清單**，不是一封一封的信 |
| 保留 | 全部歷史版本都留著 |

公告**不發放任何東西**，發放一律走信箱。

### 52.6.1 已讀怎麼判定（硬性）

**存「讀到哪一版」的版本號 `lastReadVersion`，不是 boolean。**

| 狀態 | 判定 |
|---|---|
| 有未讀 | 最新版本 > `lastReadVersion` |
| 開啟公告分頁 | `lastReadVersion` ← 最新版本 |

用 boolean「已讀／未讀」會壞在第二版：玩家讀完 v1.4 標記已讀，出了 v1.5
之後那個旗標還是 true，永遠不會再提示。版本號比大小才分得出「讀過舊的、有新的」。

初次進遊戲的角色 `lastReadVersion` 設為**當下版本**，不是 0 ——
新玩家開檔時不得出現歷史版本未讀。

## 52.7 資料

| 表 | 欄位 |
|---|---|
| `mailbox` | `id`、`characterId`、`sourceKey`（唯一）、`title`、`items[]`、`createdAt`、`claimedAt`（null ＝ 未領） |

- `sourceKey` 對 `characterId` **唯一**，重複發放靠它擋
- `items[]` 內的道具與鑲材**一律存 id 不存名稱**（§ 99.1 第 7 條）
- 公告已讀狀態存本機設定，不進 DB

### 52.7.1 換版清理（硬性）

`BUILD_INFO.version` 改變時，對每隻角色：

| 信件 | 處理 |
|---|---|
| **已領取**（`claimedAt` 不為 null） | **刪除** |
| **未領取**（`claimedAt` 為 null） | **一律保留，不分來源** |

已領取的東西已經在背包裡，那筆紀錄留著只會把列表撐長。

**未領取的絕對不可刪。** 天賦格每 5 級發一封（§ 52.2）；
玩家升到 Lv.35 拿到一封還沒點領取，這時更新版本，
照「換版清空」做會讓那個天賦格**永久消失，而且玩家不會知道自己少了一格**。
補償與里程碑同理 —— 沒領到就是沒拿到。

新版本的補償用**新的 `sourceKey`** 建立，與被刪掉的舊紀錄不衝突。

## 52.8 不做的事

| 不做 | 原因 |
|---|---|
| 遠端發放 | 沒有後端寫入端點，`leaderboard-worker` 是唯讀的 |
| 兌換碼 | 離線版的碼一定會被拆出來 |
| 每次版本更新發一封信 | 久沒玩的玩家會收到一長串沒有內容的通知（§ 52.2.1） |
| 玩家之間寄信 | 單機遊戲 |
| 未領取的信過期或被清除 | 會讓玩家永久損失天賦格且無從察覺（§ 52.7.1） |
| 領取後自動安裝天賦格 | 安裝是玩家的決定（`51-auto-talent.md` § 51.3.3） |
